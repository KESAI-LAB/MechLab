# 模块化改造 + 文献→报告模块 设计草案（讨论稿）

> 目标：现有"COMSOL 提交器"整体变成一个模块；新增「文献 PDF → Markdown → 理论报告 + COMSOL 实现报告」模块。
> 原则：**先讨论、再动手**；先跑通最小闭环，再谈质量。

## 一、整体架构：主壳 + 模块

```
app/
├─ shell.py                  # 主窗口：标题栏 + 模块切换（Notebook/侧边栏）
├─ core/                     # 共享服务
│  ├─ config.py              # 机器定义、路径、设置
│  ├─ backends.py / manager.py / runner.py   # 现有提交逻辑
│  ├─ theme.py
│  └─ settings.py            # 新增：LLM Key、pdf2md 后端选择等
├─ modules/
│  ├─ base.py                # BaseModule 接口
│  ├─ submitter/             # 现有提交器（表单/队列/日志/新机接入/演示画图）
│  │  └─ ui.py
│  └─ papers/                # 新模块
│     ├─ ui.py               # 文献列表 + 步骤按钮 + 预览
│     ├─ store.py            # SQLite：papers / reports
│     ├─ pdf2md/             # 可插拔转换后端
│     │  ├─ base.py
│     │  ├─ pymupdf4llm.py   # 轻量、无模型
│     │  ├─ mineru.py        # 高质量、需模型（可选）
│     │  └─ external.py      # 调用任意命令行
│     ├─ llm.py              # OpenAI 兼容客户端（DeepSeek/Ollama 均可）
│     ├─ report.py           # 理论报告 + 实现报告流水线
│     └─ prompts/*.md        # 提示词模板
└─ data/
   └─ papers/<paper_id>/     # source.pdf, paper.md, assets/, theory.md, implementation.md
```

### 模块接口（草案）

```python
class BaseModule:
    id: str
    title: str
    def build(self, parent: tk.Widget) -> tk.Widget: ...   # 返回模块主 Frame
    def on_show(self) -> None: ...                          # 切到该页时刷新
```

主窗口只负责：标题栏、模块切换、状态栏；模块之间不互相 import。

### 迁移步骤（低风险）

1. 把现有 `ui.py` 的界面代码整体移到 `modules/submitter/ui.py`（逻辑不变）；
2. 新增 `shell.py`，用 Notebook 挂载「提交器」一个 tab，先保证行为完全一致；
3. 全部回归：Mock 提交、一键画图、接入新机、SSH 脚本、保存全部解；
4. 再加「文献→报告」tab。

预计 0.5–1 天；风险是 UI 拆分时漏绑事件，用现有冒烟测试兜底。

## 二、PDF → Markdown：开源方案对比

| 方案 | 许可 | 公式/表格 | 中文 | 依赖/速度 | 适合 |
|---|---|---|---|---|---|
| **PyMuPDF4LLM**（PyMuPDF 2.x 内置） | AGPL-3.0 | 一般（公式多为文本，表格一般） | 好（文本层） | 无模型、秒级 | **默认轻量后端** |
| **MinerU** | AGPL-3.0 | **强**（公式 LaTeX、表格） | **强**（中文团队） | 需 PyTorch + 数 GB 模型；GPU 快 | **高质量模式（推荐可选）** |
| **Marker** | GPL-3.0（商用需授权） | 强 | 中英均可 | 需模型；GPU 快 | 英文论文、速度优先 |
| **Docling**（IBM） | MIT | 中上（表格强，公式逐步增强） | 中上 | 模型中等；CPU 可跑 | 商用友好替代 |
| **MarkItDown**（微软） | MIT | 弱 | 中 | 轻 | 快速粗提取 |
| **GROBID** | Apache-2.0 | 不转 md | 中 | Java 服务 | 只提取标题/作者/参考文献 |

参考：MinerU（<https://github.com/opendatalab/MinerU>）、Marker（<https://github.com/datalab-to/marker>）、Docling（<https://github.com/docling-project/docling>）、PyMuPDF4LLM（<https://pypi.org/project/pymupdf4llm/>）、MarkItDown（<https://github.com/microsoft/markitdown>）、GROBID（<https://github.com/kermitt2/grobid>）。

### 建议策略

- **默认**：PyMuPDF4LLM（零模型、打包简单、先跑通）；
- **高质量**：设置里可切换到 **MinerU**（外部安装，填可执行路径；力学论文公式多，值得）；
- **兜底**：`external` 后端，允许填任意命令（如已装好的 marker/docling）；
- **质量检查**：转换后做启发式检查（字符数、公式数量、表格数量、是否扫描件），差就提示切换后端；
- **公式**：保留 LaTeX；识别失败时在报告中标注"公式未识别"，不硬编。

## 三、报告生成：两阶段流水线（防幻觉）

### 阶段 1：结构化抽取（extractive）

把 `paper.md` 按章节切块，让 LLM 只做**抽取**，输出 JSON：

```json
{
  "title": "...", "authors": "...", "year": "...",
  "problem": "...", "governing_equations": [{"latex": "...", "meaning": "...", "source": "§2.1"}],
  "weak_form": [{"latex": "...", "source": "§2.3"}],
  "constitutive": [...], "parameters": [{"name": "...", "value": "...", "unit": "...", "source": "Table 1"}],
  "boundary_conditions": [...], "initial_conditions": [...],
  "geometry": [...], "mesh": [...], "solver": [...],
  "validation": [{"figure": "...", "description": "...", "source": "Fig. 5"}],
  "missing_for_comsol": ["..."]
}
```

要求：每条尽量带 `source`（章节/图/表号）；找不到就写 `unknown`，**禁止编造数值**。

### 阶段 2：生成两份报告

**理论报告 `theory.md`**：研究背景与问题、控制方程与推导链、本构与假设、弱形式、无量纲量/量级、参数表、验证基准。
**实现报告 `implementation.md`（COMSOL 专用）**：

1. 模型概述（维度、物理场接口、研究类型）
2. 几何与材料（参数表 + 来源）
3. 控制方程 → 弱形式（给出可直接填进 COMSOL 的形式）
4. 边界/初始条件
5. 网格策略与单元阶次
6. 求解器设置（稳态/瞬态、时间步、非线性、收敛判据）
7. **逐步建模路径**（Model Builder 节点树：Geometry → Materials → Physics → Mesh → Study）
8. 验证方案（对标论文图/表的具体操作）
9. **缺失信息与假设清单**（论文没给、COMSOL 必须补的）
10. 可选：COMSOL Java / MPh 脚本骨架

### LLM 接入

- 统一 OpenAI 兼容协议：`base_url + api_key + model`；
- 默认 **DeepSeek API**（便宜、中文好）；也可切 **本地 Ollama**（`http://localhost:11434/v1`，离线但质量弱）；
- 只发送相关章节（检索式裁剪），控制成本；缓存抽取结果；
- 提示词放 `prompts/`，可改；
- 每次调用记录 token/耗时到 `llm_log.jsonl`。

- `papers` 表：id、标题、作者、年份、pdf 路径、md 路径、状态、sha256、创建时间；
- `reports` 表：paper_id、kind(theory|implementation)、路径、模型、时间；
- 界面：左侧文献列表 + 导入按钮；右侧三个步骤按钮（① 转 Markdown ② 理论报告 ③ 实现报告）+ 预览区 + 导出。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 公式/表格识别差 | 默认轻量 + 可切 MinerU；报告标注未识别项 |
| LLM 编数据 | 两阶段抽取、要求来源、参数表独立校验 |
| API 费用/网络 | 只发相关章节 + 缓存；支持本地 Ollama |
| 扫描版 PDF | 先检测文本层，无文本提示走 OCR（MinerU/Tesseract） |
| 打包体积 | 只内置 PyMuPDF4LLM；MinerU 作为外部可选工具 |
| 许可（AGPL/GPL） | 课程/内部使用没问题；对外分发需注意，Docling(MIT) 可作替代 |

## 九、MinerU 后端与图片处理（2026-11-09 续）

- **MinerU 2.7.6 后端已完成并实测**：独立 venv `.venvs/mineru`（uv 解析依赖），模型缓存 `.venvs/modelscope`（约 3.5 GB），配置 `.venvs/mineru/mineru.json`；适配器支持 `-b pipeline -d cpu`、页范围 `-s/-e`、超时与设备配置。
- **实测（CPU）**：同一篇 TRISO 论文前 3 页 → 12,923 字符、4 个 `$$` 公式块、84 处行内公式、4 张图，耗时 163 s（含模型加载）；对比 PyMuPDF4LLM 数学输出明显更完整。
- **环境坑**：后台沙箱禁止写 `C:\Users\...\AppData`，因此把 Ultralytics / matplotlib / torch / HF 缓存与 MinerU 配置全部重定向到项目 `.venvs/` 内；pip 缓存异常时用 `--no-cache-dir` 或 uv。
- **图片**：PDF→MD 阶段把图抽到 `assets/` 并在 paper.md 中引用；新增 `figures.md`（图注清单）拼进报告提示词。**报告生成阶段模型仍不直接读图**（DeepSeek 网页自动化为纯文本），图像内容靠图注/正文间接体现。
- 安装脚本：`scripts/setup_mineru.ps1`（建 venv → 装 MinerU → 下载模型 → 写配置）。

## 十、报告插入原文图（B 档，2026-11-11）

- **图号映射**：`pdf2md/captions.py` 生成 `figures.json`：
  - MinerU：解析 `mineru_raw/**/*_content_list.json` 的 image 块（`img_path` / `image_caption` / `page_idx`），一篇 10 图全部正确编号；
  - PyMuPDF4LLM：从 paper.md 按图片链接就近匹配 `Fig.` 图注，仅兜底（实际只匹配到 3/10，精度有限）。
- **报告生成**：提示词要求模型在讨论图的段落后单独一行输出 `[[FIG:n]]`（只允许清单内图号、不堆文末、不放代码块）；`report.insert_figures` 替换为 `![Fig. n](assets/xxx.jpg)` + 图注斜体，并校验缺失图号、把误入代码块的图片块移到代码块之后、平衡代码围栏。
- **实测**（MinerU 版论文）：理论报告插入 9 张、实现报告插入 7 张；图片路径全部存在、无残留占位符、无图片落在代码块内。
- **导出**：`导出 Markdown…` 会复制 `assets/` 与 `figures.json/md`，Obsidian 中可直接显示。
- 已知限制：模型只能靠图注判断插图位置，可能不够贴切；PyMuPDF 后端图号映射不完整，插入图片建议用 MinerU。
